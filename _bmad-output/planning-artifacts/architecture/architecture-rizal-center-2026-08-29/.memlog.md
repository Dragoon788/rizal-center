- (decision) A one-off event is an INSTANT; a recurrence is a RULE IN LOCAL TIME. Different things, different storage. Binds: how recurring times are persisted. Prevents: the DST bug -- stepping a UTC instant by 7 days silently moves a 7pm class to 6pm when Chicago leaves DST, and nobody notices until members arrive at an empty room. - (decision) The recurrence rule is ONE self-contained object field on event, revealed by the toggle -- not a reinterpretation of startDate/endDate. startDate/endDate keep exactly one meaning (the one-off instant). - (version) WEB-VERIFIED 2026-08-29 sanity.io/docs/content-lake/live-content-api: Live Content API is GA and available on ALL plans including Free. Mechanics: clients subscribe to 'sync tags' (content identifiers mapped to requests); a dataset change fires matching tags and the client refetches. next-sanity's defineLive/sanityFetch wrap it. Live connections themselves consume no quota but the resulting refetches DO count as API requests. Free and Growth retain events 15 minutes. CAVEATS: no dataset aliases (real names only); docs advise site-wide caching 'to prevent usage spikes'; CDN setups need extra configuration. CRITICAL: by DEFAULT it revalidates in the BACKGROUND -- 'some users see stale content until revalidation completes'. Guaranteeing fresh everywhere requires deploying an Invalidate Sync Tags Sanity Function and setting waitFor='function'.
- (decision) REJECT the Live Content API for this project; keep webhook-driven revalidation from Fork 1. Reasons, in order: (1) it does NOT deliver Francis's stated requirement -- never serve stale -- out of the box; its default is background revalidation, the exact SWR behaviour he objected to, and fixing that needs an added Sanity Function plus waitFor='function', so it is MORE parts, not fewer; (2) its cost model is per-visitor -- a live subscription per browser, with every content change fanning refetches to every connected client -- which is precisely the per-visitor scaling Fork 1 deliberately avoided; (3) Sanity's own docs warn to use site-wide caching to prevent usage spikes; (4) it reintroduces client-side JS on every page against PRD 13. It is built for content that changes while a visitor watches (live blogs, inventory, scores); the Rizal Center publishes a few times a week to visitors who arrive, read and leave. Revisit if the site ever gains a genuinely live surface.
